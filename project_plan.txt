0. DECISION LOG
══════════════════════════════════════════════════════════════════════════════════════════════
- LLM provider: Groq API (via langchain-groq).
    Models (set in .env, 2026-10-26): strong = openai/gpt-oss-20b, fast = qwen/qwen3.8-27b.
    Note: Groq has no embeddings API, so embeddings come from a local model
    (e.g. sentence-transformers / FastEmbed). Free and no extra API key.
- Agent framework: LangGraph for the orchestrator and internal agents (no LlamaIndex, no ADK/AutoGen).
    The Email agent is a SEPARATE service talking A2A, built with CrewAI (decided 2026-10-26).
    A2A is framework-agnostic: a LangGraph client talking to a CrewAI server shows exactly that.
- Frontend: simple React app (Vite).
- Evaluation & reporting: ADDED. Every agent gets a small eval set and a metrics report (Section 5).
- SQL safety: ADDED. DB-level read-only role + query parsing, not just string checks.
- A2A spec: verify current spec version & method names at the start of Phase 5
  (early drafts used /tasks/send; newer versions use JSON-RPC methods like message/send).
- Hybrid search: corrected to dense (embeddings) + sparse (keyword/BM25), fused with RRF.
- HITL flow: detailed design to be done before Phase 6 (see Section 3-F).
- Local email: Mailpit (fake SMTP inbox in Docker) instead of real email during development.
- Quality: pytest tests, GitHub Actions CI, DB seed script, strong README.

1. EXECUTIVE SYSTEM OVERVIEW
══════════════════════════════════════════════════════════════════════════════════════════════
A multi-agent platform with clearly separated concerns:

- Core Brain: a central LangGraph orchestrator (supervisor) behind a FastAPI gateway.
- Internal leaf agents (run inside the orchestrator service):
    * Database Agent   — safe Text-to-SQL over PostgreSQL.
    * Doc QA Agent     — layout-aware PDF ingestion + hybrid RAG with citations.
    * Web Search Agent — reaches live web data through MCP (DuckDuckGo MCP server).
- External service (A2A protocol):
    * Email & Dispatch Agent — standalone CrewAI service on its own port.
      Exposes an A2A interface (agent card, task lifecycle, artifacts).
      Drafts emails, runs policy/PII checks, and requires human approval (HITL) before sending.
- Frontend: React dashboard for chat, document upload, and approving email dispatches.
- Observability: Langfuse traces across the orchestrator AND the A2A email service.
- Evaluation: per-agent eval sets with a generated metrics report.

Protocols, in one line each:
- MCP = an agent reaching DOWN to tools/data.
- A2A = an agent talking ACROSS to another agent in another service.

3. COMPONENT PLAN
══════════════════════════════════════════════════════════════════════════════════════════════
A. Central Orchestrator (LangGraph + FastAPI)
   - LangGraph StateGraph acting as a supervisor.
   - Typed state: user query, planned sub-tasks, results per agent, final answer, messages.
   - Conditional edges route to the right agent(s); can run agents in parallel (Scenario 2).
   - Checkpointer (Postgres) persists graph state per session, which is needed for memory AND HITL.
   - FastAPI streams progress and tokens to the frontend via SSE.
   - LLM: Groq. Pick models at Phase 0 from Groq's current model list
     (a stronger model for routing/SQL, a small fast one for cheap steps).
   - Groq free tier has rate limits: add retry with backoff from day one.

B. Database Agent (PostgreSQL)
   - Tables: invoices, vendors, users, tickets, audit_logs (filled by a seed script).
   - Flow: reflect schema -> generate SQL -> validate -> execute -> validate rows -> return.
   - Safety (defense in depth):
       1. Connect with a dedicated Postgres role that has SELECT-only grants.
       2. Parse SQL with sqlglot; reject anything that is not a single SELECT.
       3. Enforce a LIMIT and a statement_timeout.
       4. On SQL error, feed the error back to the LLM for one or two self-correction retries.
   - Async driver (asyncpg / psycopg async). Output validated with Pydantic.

C. Doc QA Agent (Document Intelligence)
   - PDF upload via FastAPI multipart endpoint.
   - Layout-aware parsing to markdown, keeping headers and tables
     (candidate libraries: Docling or pymupdf4llm; decide in Phase 3).
   - Chunking by document structure (sections), with metadata (file, page, section).
   - Hybrid retrieval: dense (local embeddings in pgvector) + sparse (BM25 / Postgres full-text),
     merged with Reciprocal Rank Fusion (implement RRF ourselves to learn it).
   - Answers must cite chunks (file + page). If the evidence is weak, say "not found".

D. Web Search Agent (MCP)
   - Connects to a DuckDuckGo MCP server using langchain-mcp-adapters.
   - Discovers tools at runtime (search, fetch page) instead of hardcoding API calls.
   - Learning bonus: write our own tiny MCP server to understand the protocol from both sides.

E. Email & Dispatch Agent (separate CrewAI service, A2A server)
   - Own process, own port, own requirements, so it is a genuine service boundary.
   - Serves an Agent Card at /.well-known/agent-card.json describing its skills.
   - Orchestrator is the A2A client: discovers the card, sends a task, tracks task state.
   - Drafts email -> PII masking + tone/policy checks -> waits for approval -> sends via SMTP.
   - Dev: SMTP goes to Mailpit (view mails at its web UI). Real provider (e.g. Resend) optional later.
   - Use the official A2A Python SDK; confirm current spec at Phase 5 start.

F. Human-in-the-Loop (HITL) flow — DETAILED DESIGN TO DO BEFORE PHASE 6
   Known challenge: TWO things pause at the same time.
   - The email service puts its A2A task into "input-required".
   - The orchestrator graph must also pause (LangGraph interrupt + checkpointer) and save state.
   - Frontend shows the draft; Approve/Reject/Edit hits the FastAPI resume endpoint.
   - Gateway resumes the graph -> graph continues the A2A task -> email sent -> task "completed".
   Open questions for the design session: where the pending-approval record lives, timeouts,
   what "Edit" means (re-draft vs manual edit), and what happens on reject.

G. Observability (Langfuse, self-hosted in Docker)
   - Langfuse callback on the LangGraph runtime; tracing in the email service too.
   - Propagate trace context over the A2A HTTP call so the whole flow is ONE trace:
     Router -> DB Agent -> A2A call -> Email draft -> Approval wait -> Dispatch.
   - Track tokens, latency per step, and cost (Groq prices may need custom model
     definitions in Langfuse).

5. EVALUATION & REPORTING
══════════════════════════════════════════════════════════════════════════════════════════════
   Goal: turn "I built it" into "I measured it". The numbers go into the README and resume.
   - Text-to-SQL: ~25 questions with expected results -> execution accuracy.
   - Doc QA RAG: ~20 questions with known answer pages -> retrieval hit rate@k,
     answer faithfulness / citation correctness (LLM-as-judge + manual spot checks).
     Compare dense-only vs BM25-only vs hybrid. This comparison is a strong interview story.
   - Router: ~20 prompts with the expected agent(s) -> routing accuracy.
   - Report: a script (evals/run_all.py) that runs every eval and writes a markdown report
     with metrics, latency, and token usage. Optionally push scores to Langfuse.

6. EXECUTION SCENARIOS
══════════════════════════════════════════════════════════════════════════════════════════════
Scenario 1: Multi-hop DB lookup + A2A email dispatch (with HITL)
   Prompt: "Query the database for all pending vendor invoices due this week, summarize them,
            and send an email draft to accounts@company.com."
   1. Orchestrator plans two steps: DB retrieval, then email dispatch.
   2. DB Agent: schema -> safe SQL -> returns e.g. 3 pending invoices.
   3. Orchestrator summarizes and builds the email task payload.
   4. A2A: orchestrator sends the task to the Email service.
   5. Email service drafts + checks -> task state "input-required". Orchestrator graph pauses.
   6. Frontend shows "Email drafted for accounts@company.com. Review & approve."
   7. User clicks Approve -> gateway resumes graph -> A2A task continues.
   8. Email sent via SMTP (Mailpit) -> task "completed" with a delivery receipt artifact.
   9. Orchestrator shows confirmation to the user.

Scenario 2: Document intelligence + live web verification via MCP
   Prompt: "Upload this quarterly compliance PDF, check our stated cloud vendor policies, and
            search the web to see if the vendor updated their SLA terms recently."
   1. Orchestrator runs Doc QA and Web Search (parallel where possible).
   2. Doc QA: hybrid search over the PDF -> vendor name + SLA terms with citations.
   3. Web Search: DuckDuckGo via MCP -> recent public SLA updates.
   4. Orchestrator compares both and highlights compliance gaps, citing both sources.

10. WHY THIS STANDS OUT IN INTERVIEWS
══════════════════════════════════════════════════════════════════════════════════════════════
- Architecture: separate services and standard protocols, not one giant script.
- Clear protocol story: MCP for tools (down), A2A for agent-to-agent (across).
- Safety: read-only DB role + SQL parsing; human approval before irreversible actions.
- Measured, not just built: eval report with real numbers (SQL accuracy, retrieval hit rate,
  routing accuracy, hybrid vs dense comparison).
- Observability: one Langfuse trace across services, with tokens, latency and cost.
